# Milestone 1 completion report

## Implementation

Established the Rust workspace, CLI, strict JSON configuration, immutable window
and tick contracts, deterministic f64 CPU multi-window model and native export
validator. The model implements local positions/RoPE, configurable window identity,
local transformer blocks followed by global attention, separate prediction queries,
phase ordering, durable memory, NOOP, external input, replacement and EOS eviction.

The CLI can validate/replay exports or execute an embedded canonical demo. The
headless HTTP server serves real status, CPU discovery, explicit capability states,
OpenAPI and event schemas. The responsive dashboard uses those public endpoints
and four workspace views. Unimplemented execution requests have no effects and
return structured 501 errors. The server cannot bind remotely or execute tools.

## Architecture

Five application crates separate core semantics, datasets, numerical reference,
HTTP and CLI. A sixth independent feature-gated crate probes Burn; it is absent
from the CLI's dependency graph. No Python runtime, unsafe Tesslot code, frontend
build chain, empty subsystem crates or mandatory GPU dependency was introduced.
See [architecture](architecture.md) and [ADRs](decisions/0001-foundation.md).

## Backend findings

Burn 0.22.1 with Flex is the recommended next candidate. Its executable CPU probes
validate matmul/backward, attached prefix gradients, masking and basic operation
checkpointing. It has a differentiable device-copy implementation in inspected
source, but no real cross-device result here. Its dynamic Device API and deprecated
NdArray backend required using the current interface rather than older examples.
Candle's Qwen3 and device-copy backward sources were inspected; LibTorch/tch is an
alternative requiring its own executable gates. No production backend is selected.
See [evaluation](backend-evaluation.md) and [required gates](decisions/0002-backend-gates.md).

## Validation results

* Workspace build, formatting, Clippy with warnings denied and **24 CPU tests** pass
  on Linux x86_64 with Rust 1.99.1. These include four opt-in Burn probes.
* Rust visibility agrees with **all 184041** query/key decisions generated by the
  actual upstream predicate, including closure and removal boundaries.
* Full/incremental/cached/recomputed numerical paths agree within 1e-12. Default
  demo: 73 ticks, four windows, 429 rows, 25 chunks; observed max error **0.0**,
  effective target weight **82.95**, reference loss approximately **4.97479879**.
  These are untrained teacher-forced CPU measurements, not training results.
* Canonical and 2050-tick/4103-row exports validate; malformed/duplicate/incomplete
  inputs fail. Seeded bounded shuffling retains complete sample boundaries.
* Live server HTTP responses validate against the published schemas. Chromium
  checks pass for status, all workspaces, invalid hash fallback, mobile layout,
  disconnect and reconnect. JavaScript syntax and Git whitespace checks pass.
* GPU, production training, persistence and tool execution are not verified.

The detailed commands and tolerance rationale are in [testing](testing.md).

## Trajectory compatibility

Fixtures were produced by the unmodified Trajectory Remix compiler/exporter at
`d2c8083536d56a33d876e2650ae855722d491566`, not manually approximated. Supported
modern records preserve unshifted labels, fractional effective weights, excluded
observations, parallel windows, external-first visibility, durable-only cache,
headers, late opens, closures, NOOP and replacement metadata. The reader checks
tokenizer/control compatibility, slot/lifecycle mapping, row arrays, ordering,
chunk prefixes and completeness. Reproducible source/generator/hash manifests are
checked in. [Compatibility details](trajectory-compatibility.md) list strict
version handling and deferred metadata/packing features.

## Limitations and risks

The model is a tiny f64 single-head oracle, not a Qwen3 implementation. Its query
seed and normalization choices are versioned research defaults. No model-gradient
trainer, model/checkpoint importer, optimizer, persistent database, resource
allocator, production sampling, SSE/WS, subagent or real tool exists. CUDA placement
is explicitly rejected; CPU budgets are declarative, not enforced admission limits.
All unavailable metrics stay unavailable/null. Remote authentication is not
implemented; remote binds are prohibited.

The validator materializes one trajectory and retains seen IDs; huge corpora need
disk-backed indexing. Buffered shuffle is deterministic but not globally uniform.
The dense reference CLI caps replay at 4096 rows. Tokenizer identity currently
comes from trusted metadata, not native tokenizer loading. Legacy missing-slot
exports, packed sample tensors and full artifact provenance sidecars are deferred.
Checkpoint/persistence and hardware suites are not replaced by placeholder tests.

## Next steps

1. Port the tiny architecture to a real autograd backend and finite-difference all
   trainable parameters, with rowwise oracle parity and attached chunk loss.
2. Test real asymmetric two-GPU forward/backward/optimizer behavior and actual
   communication before coupling production execution to a framework.
3. Prove architecture-level recomputation/gradient parity and measure memory.
4. Load actual HF configuration/tokenizer/SafeTensors metadata; validate conversion,
   tied embeddings, dedicated controls and seeded new components with tiny fixtures.
5. Implement Qwen-derived single-device forward/backward and CUDA precision/cache
   equivalence tests. Optional large weights still require explicit authorization.

[The roadmap](roadmap.md) subdivides subsequent SFT, checkpoint, multi-GPU,
inference, agent and evaluation work into independently testable milestones.
