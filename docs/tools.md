# Tool compatibility and production boundaries

No production tool executor is implemented in milestone 1. This matrix was reviewed against the pinned upstream registry; [complete author schemas](../fixtures/tool-schemas.json) retain exact types, limits, alternatives, invisible arguments and descriptions. The argument summaries below are abbreviated; `?` means optional. They are not a replacement for the JSON schemas.

Synthetic `run(args,state,windows)` returns `(output,is_done,modified_state)` once per logical tick. Execution begins after the last request token; results enter B, while EOS closes/cancels after D. Production adapters must preserve context insertion and cancellation ordering while using actual wall-clock deadlines and asynchronous services. They will not sleep for synthetic token delays. Earlier completed side effects remain committed after cancellation. Author-only controls remain replay/test inputs.

Production tool schemas will be independently versioned. Preserve names and argument conventions when feasible, but record explicit versioned differences rather than accepting author-only arguments. Public discovery must remove invisible arguments and their required entries. Registry discovery is not authorization.

Future tools may stream intermediate observations and execute concurrently. Use typed operation IDs, isolated execution budgets, permission checks, timeout/cancellation cleanup and auditable effects. Context observations enter only in a scheduled B phase; tool wall time is not a model tick. [Security requirements](security.md) must pass before any dispatcher becomes reachable.
